# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

Пользователи:
* могут удалённо включать/выключать отопление в своих домах

Система:
* переключает включенность отопления в доме пользователя в соответствии с поступившей от пользователя командой

**Мониторинг температуры:**

Система:
* получает данные о температуре с датчиков, установленных в домах пользователей

Пользователи:
* могут удалённо просматривать текущую температуру в своих домах

### 2. Анализ архитектуры монолитного приложения

* Язык программирования: Java 17, фреймворк Spring
* База данных: PostgreSQL
* Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными)
находятся в рамках одного приложения.
* Взаимодействие: Синхронное, запросы обрабатываются последовательно.
* Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
* Развёртывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

* домен: пользователи
  * регистрация в системе, установка настроек своего аккаунта (логин, пароль, язык интерфейса, единицы измерения с датчиков) 
  * авторизация

* домен: устройства
  * (администрирование) для устройства модели X установка значений настроек по умолчанию, которые экземпляр такой модели получит от сервера при выпуске устройства, либо при первом подключении к аккаунту дома

* домен: сценарии и действия
  * (администрирование) создание/редактирование действий, который можно совершить с "устройством" типа `X` на моделях `X1`, `X2`, ...

* домен: умный дом
  * поддомен: настройки дома
    * создание нового дома (активный пользователь в качестве администратора по умолчанию)
    * комнаты, геолокация дома
    * уведомления
    * интеграции со сторонними приложениями
  * поддомен: пользователи
    * добавление/удаление пользователей в аккаунт дома
    * permissions:
      * создание групп пользователей, ролей, привязка к ним прав/ограничений
      * установка/удаление ролей/групп на пользователя
  * поддомен: устройства
    * привязка/отвязка устройства к аккаунту дома
    * установка настроек для устройства в контексте дома (привязка к комнате, своё имя, режим мощности, ...) 
  * поддомен: события
    * "устройства" с определённой частотой отправляют своё состояние/измеряемые данные
    * подписка: можно подписаться на оповещение о событии, подходящем по определённым критериям (от устройства X, содержит тип события или значение из диапазона)
  * поддомен: сценарии, действия, триггеры
    * создание/редактирование сценариев (с нуля, либо на основе "готовых"), воспроизводящих определённые действия по триггеру (ручной запуск, либо как реакция на событие)

### **4. Проблемы монолитного решения**

Стандартные проблемы монолита:
* невозможно деплоить только часть приложения (микросервис) - нужно пересобирать и поднимать 1 большое приложение
* тяжелее ограничить падение какой-то одной областью (микросервисом), упасть может весь инстанс
* изменения могут непредсказуемо затрагивать что-угодно, поэтому тестировать нужно дольше, а риск ошибки выше
* нельзя масштабировать только наиболее нагруженные части (serverless/микросервис) - увеличить можно только количество больших инстансов
* хуже с разделением зон ответственности и обучаемостью при росте количества команд: проще делить отдельные сервисы, чем директории внутри одного сервиса; но решается и модульным монолитом 

Стандартные проблемы синхронного взаимодействия:
* блокирует выполнение пока не будет получен ответ, увеличивает время отклика системы 
* масштабирование: каждый запрос требует немедленного ответа, сервер может выдержать лишь определённое количество одновременных операций
* сбой сервиса, к которому вызов был направлен, означает потерю операции; в случае шины операция бы лежала в очереди до тех пор, пока не была бы успешно обработана
